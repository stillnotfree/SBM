# SBM contributor guide

## Read first

- Treat this file as a map, not a replacement for the source and tests.
- Read `README.md`, `ARCHITECTURE.md`, `SECURITY.md`, and the touched code.
- Read `docs/development.md` before changing build or release behavior.
- Treat imported profiles, subscriptions, URIs, and routing JSON as untrusted input.
- Preserve unrelated work in a dirty tree. Never discard changes to make a test pass.

## Product boundary

- SBM is a native Swift/SwiftUI menu-bar client for Apple Silicon and macOS 26+.
- It is TUN-only and runs one pinned sing-box core.
- The UI process is unprivileged.
- A narrow versioned launchd helper owns the protected root runtime.
- There is no Xray core, system-proxy mode, Web UI, dashboard, telemetry,
  traffic analytics, access logging, MITM, or HTTPS interception.
- Do not add hidden protocol fallback, automatic server rotation, or speculative
  network tuning.

## Repository map

- `Sources/SBM/`: app state, UI, subscriptions, persistence, updates, diagnostics.
- `Sources/SBMShared/`: bounded IPC and shared typed data.
- `Sources/SBMHelper/`: validation, composition, protected runtime, helper entry.
- `Tests/SBMTests/`: unit, security, lifecycle, packaging, and regression tests.
- `Examples/`: deliberately small user-owned routing examples.
- `scripts/`: core update, performance sampling, and release preflight.
- `Resources/`: bundle metadata, icon assets, and launchd plist.
- `Core.lock`: exact reviewed upstream core version and input digests.
- `ARCHITECTURE.md`: current security and process-boundary design.
- `docs/research/`: evidence that can inform work but is not product policy.

## Security invariants

- Never run sing-box or a shell from the UI process.
- Never accept command strings, arbitrary paths, environments, or arguments over IPC.
- Keep IPC versioned, typed, length-bounded, authenticated, and fail-closed.
- The helper may execute only the verified core at its fixed protected path.
- Root-owned runtime files stay under `/Library/Application Support/SBM`.
- Candidate config and core replacements must be staged, validated, atomic, and recoverable.
- A failed activation must not destroy the last known-good config or core.
- Unknown profile types, fields, capabilities, and future core behavior fail closed.
- Do not pass raw core validation output, logs, credentials, or profile bodies to the UI.
- Cross-origin subscription redirects must strip sensitive request headers.
- Diagnostics must be bounded, redacted, probe-free, and derived from existing state.
- Never put real subscription URLs, HWIDs, private keys, or credentials in tests or docs.

## Runtime invariants

- Persisted desired profile, routing mode, node, and policy must converge with helper state.
- Do not report a setting as active until the helper confirms the applied generation.
- Serialize or generation-order overlapping runtime changes; stale replies cannot win.
- Disconnect is durable and must not be undone by refresh or automatic recovery.
- Automatic recovery is bounded to one persisted attempt until explicit reconnect.
- Do not stop, restart, replace, or probe an installed SBM runtime during local work.
- Local tests and `dist/SBM.app` are not proof about an installed app or live VPN.

## Profile and routing rules

- Managed node identity is distinct from display name and source position.
- Identity must survive refresh, reorder, source rename, and equivalent URI spelling.
- Secret material must not be recoverable from an identifier.
- Unsupported URI semantics must produce an explicit error, never a silent downgrade.
- Imported routing may target only `direct` or the app-controlled selected proxy.
- Safety rules precede app rules; app rules precede imported rules; final comes last.
- A routing explanation must evaluate the final composed route, not only source JSON.
- Runtime-dependent rules produce an indeterminate explanation when context is absent.
- DNS routing and traffic routing are related policies, not interchangeable results.

## Core and generated files

- Update the core only with `scripts/update-core.swift stable` from the repository root.
- Never hand-edit `.vendor/` artifacts.
- `Sources/SBMShared/CoreBuildInfo.swift` is generated by `make core`.
- `dist/`, `.build/`, `.swiftpm/`, `.vendor/`, DMGs, and `.DS_Store` are ignored outputs.
- Core changes require exact stable version, archive digest, binary digest, version,
  architecture, signing, embedded digest, and packaging checks.

## Editing workflow

1. Record `git status --short` and inspect the relevant diff.
2. Trace the concrete behavior through source and existing tests.
3. Add a deterministic failing regression for a confirmed defect.
4. Make the smallest change that restores the stated invariant.
5. Run the focused tests for the changed boundary.
6. Review `git diff`, run formatting lint, and run `git diff --check`.
7. Run the full suite before claiming completion.

## Standard commands

```sh
swift test
xcrun swift-format lint --recursive Sources Tests Package.swift
git diff --check
plutil -lint Resources/Info.plist Resources/com.stillnotfree.sbm.helper.plist
make app
make release-check TAG=vX.Y.Z
```

- Use `make release-check` only after repository metadata matches the proposed tag.
- The release gate builds locally; it does not install, run, publish, tag, or push.
- Performance claims require the protocol in `docs/PERFORMANCE.md` and an A/B baseline.

## Change discipline

- Correctness and security precede convenience, abstraction, and micro-optimization.
- Do not add dependencies when Foundation or a small local type is sufficient.
- Keep parsing, validation, policy composition, persistence, and UI presentation separate.
- Prefer typed errors and explicit states over free-form status strings.
- Bound collections, strings, recursion, files, downloads, messages, and timeouts.
- Preserve atomic writes and safe-permission checks in user and root stores.
- Keep platform behavior isolated behind small interfaces where deterministic tests need it.
- Avoid title-only AppKit window discovery when a stable scene or window identifier exists.

## Research and claims

- Telegram observations are evidence, not specification.
- Separate confirmed code/core facts, reproducible observations, hypotheses, and folklore.
- Verify changing facts against current authoritative upstream source or documentation.
- Do not claim universal censorship behavior, protocol superiority, or performance wins.
- Document limitations and uncertainty next to the feature they constrain.

## Publication boundary

- Do not commit, push, tag, publish, install, or create a release without explicit approval.
- Keep `.codex/` and local review artifacts out of commits.
- A release needs a clean intentional diff, full local gate, DMG, and SHA-256 evidence.
- Never manipulate the installed app, helper, sing-box, or their launchd state during release prep.

## Definition of done

- The confirmed defect has a regression or the new behavior has deterministic coverage.
- Security invariants and migration behavior are preserved.
- Focused tests, full tests, format lint, plist lint, and diff checks pass as applicable.
- Documentation describes actual behavior and explicit limitations without marketing claims.
- Remaining risks and unverified live-GUI or network behavior are reported honestly.
